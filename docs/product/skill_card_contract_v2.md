# 技能卡契约 v2（执行层）

> 范围：**执行层**。前提核验与成果核验按既定口径**后置**，本页不定义它们的结论权。
> 兼容原则：**旧字段原样保留，新增 `contract_v2`**。每次执行必须显式记录 `contract_generation`
> （`legacy` / `v2`）；禁止隐式回退，禁止两代同跑一次。

## 1. 为什么要有 v2

现状：卡里写死完整流程（`assembly: fixed`），模型只能填空；成功判据是单点比较。
执行层要成立，卡必须从「一条固定流程」变成「一条已登记方法 + 可构造空间 + 工具面 + 证据与义务」。

一个指定方法 = 一个**逻辑技能卡**；卡内可有多个**实现变体**；跨方法复用走**工具契约**。

## 2. 三代关系

| 代际 | 生效内容 | 规则 |
|---|---|---|
| `legacy` | 原有字段与旧执行器 | 保持原有解释，历史记录可回放 |
| `v2` | `contract_v2` 与 V2 执行协议 | 不触发旧固定流程；不把旧 `judge` 当完成依据 |

旧解析器若拒绝未知字段，由**兼容适配器**提供仅含旧字段的投影视图；卡原文与版本始终可追溯。

## 3. 字段总表

“必填”指 V2 发布要求。列表类字段即使为空也必须显式给出，避免把“未声明”当成“不需要”。
填写者：**维** = 维护者，**程** = 程序，**模** = 模型（模型只写运行记录，不改静态边界）。

| 字段 | 类型 | 必填 | 语义 | 程序机械校验 |
|---|---|---|---|---|
| `schema_version` | string | 是 | 契约格式版本 | 解析器支持 |
| `card_id` | string | 是 | 逻辑卡稳定标识 | 唯一性；与 `method_ref` 映射 |
| `card_version` | string | 是 | 卡发布版本 | 发布后内容不可原地修改 |
| `content_id` | string | 是 | 不可变内容标识 | 可解析到确切内容 |
| `catalog_entry_ref` | string | 是 | 发布目录条目 | 状态与修订可追溯 |
| `owner` | string | 是 | 维护责任方 | 非空 |
| `method_ref` | obj `{id, version}` | 是 | 绑定的已登记方法 | 与图给定方法精确匹配 |
| `execution_model` | enum | 是 | 本方案为 `model_constructed` | 取值合法 |
| `phase_usage` | string[] | 是 | 本轮为 `["execution"]` | 当前阶段被允许 |
| `compatibility` | obj | 迁移卡必填 | 旧引用、输入映射、代际分派 | 映射有效，无隐式降级 |
| `promise` | obj | 是 | 能力承诺、目标边界、产出、排除项 | 与方法契约一致 |
| `input_sources` | obj | 是 | `task` / `observation` / `model` 三类输入 | 来源、类型、取值时点 |
| `observation_policy` | obj | 是 | 观察信封、时效、失效条件、未知处理 | 来源引用、主体绑定、时效 |
| `observation_sources` | obj | 改造中（见下表注） | 每个观察输入：事实契约、**已登记**派生规则、主体绑定、可接受证据 | 规则必须已在 `runtime/observation_rules.py` 登记；事实契约与规则一致；观察名必须是本卡声明的输入 |

| `construction_space` | obj | 是 | 允许构造什么、不得改变什么 | 结构约束可表达 |
| `call_preconditions` | obj | 是 | 调用前必须成立的条件 | **每次调用重新检查** |
| `outputs` | obj | 是 | 输出结构 | 结构与条件必填项 |
| `evidence` | obj | 是 | 必需记录、主张所需引用、缺证说明 | 引用存在、来源正确、关联完整 |
| `failures` | obj | 是 | 失败与效果未知的区分 | 状态枚举；禁止程序擅自换实现 |
| `idempotency` | obj | 是 | 幂等条件、键、作用域、窗口 | 是否满足所声明条件 |
| `lifecycle` | obj | 是 | 清理、恢复、保留、责任转移 | 义务登记、到期条件、解除凭据 |

发布状态（`active` / `deprecated` / `retired`）记在 `catalog_entry_ref` 指向的发布目录里，
**状态可变，卡内容不可原地变**。

## 4. 四个复用子结构

| 子结构 | 字段 | 约定 |
|---|---|---|
| 输入定义 | `schema`、`required_before`、可选 `default`/`sensitivity` | 时点至少区分：首次调用 / 修改动作前 / 每次调用；未知观察不得填默认真值 |
| 观察实例 | `value`、`subject_ref`、`transport_ref`、`observed_at`、`raw_record_ref` | 原始返回由程序保存；模型推导的观察另带主张与来源引用 |
| 条件谓词 | `id`、`input`、`op`、`value` | 只用登记谓词，**条件里不允许塞任意脚本** |
| 生命周期义务 | `id`、`applies_to`、`due`、`discharge` | 对应条件标识必须有定义，不能只靠自然语言 |

## 5. 硬约束（校验器会拒）

### 5.0 准入条件 vs 结果条件（桥 run322 定案）

一条命题如果**只能靠把这件事做出来才能证明**，它就不能同时是"做这件事之前必须为真"的门。redis 卡的
`write_without_auth`（"这个服务接受未鉴权改动"）与 `readback_supported`（"改动能同源回读"）就是这种命题：
把它们留在 `applicability.common` 里，方法在真机永远启动不了（程序会按"未知只许观察"拒绝第一次改动）。

所以卡必须把它们移出准入集合，写进 `applicability.established_by_this_method`：准入条件只留**事先成立得了**的
（目标/边界已绑定、位置与作用域、工具精确绑定、观察信封完整）。程序在**完成主张**之前检查结果条件是否已被
证据成立；没成立就不许声称完成（`submit_partial` / `submit_indeterminate` / `blocked`，或带需要项移交）。

`observation_sources` 是配套的"观察从哪来"声明：每个观察输入写清它对应哪个**事实契约**、由哪条**已登记规则**
派生、绑定在谁身上、接受哪些工具契约的回执。没有声明来源的观察 = 没有供给者，运行层如实报
`FACT_PROVIDER_UNAVAILABLE`，**不许猜一个值**；模型可以提议采集动作，但不能写观察值。
1. `failures.automatic_business_retry` 与 `automatic_business_fallback` **必须为 false**。
2. `evidence.final_verification` 与 `submission.final_graph_satisfaction` **必须为 `deferred`**（核验后置）。
3. 义务不得把“后置”当借口：`due: before_claimed_complete` 的义务未解除时，不得提交无保留的完整主张。
4. `idempotency.guarantee` 只能声明**工具契约与提供方实际支持**的保证；不得由卡单方面“声明出”幂等。
5. 变体可以补充义务，**不得削弱**方法契约中的要求。
6. 混淆/验收标签（`is_decoy`、`gold`、`expected_reject` 等）**不得出现在卡内容或索引里**，只存在于验收 oracle。

## 6. 混淆卡（相关但不相同）的四条纪律

1. 每个混淆条目必须在**某个合理现场真实适用**（要配一条正例：改掉版本/平台/前提后应成为合法候选）。
2. 每次**只改一个主要区分因素**，失败时才能分辨是版本、平台、语义还是前提处理出了问题。
3. **合法替代实现是正例**：两变体都满足任务时用「允许集合」判定，不得为维持唯一答案把其一标成负例。
4. 候选之间的文档长度、字段完整度、命名风格要**接近**，避免靠外观就能筛掉。

四类：同服务不同版本 / 同技术不同平台 / 名称相近但语义不同 / 前提不满足的近亲。

特别要区分：同主机身份 vs 容器内身份；容器身份 vs 宿主身份；同一凭据在不同目标上的有效性；
起点不可直达 vs 经已建立访问上下文可达；工具“存在”vs 该实现适用当前平台。

## 7. 检索验收（执行层）

一条用例 = `fixture`（任务、现场、目录、工具返回）+ `oracle_private`（允许集合、预期事件、禁止事件）。

两个指标（**不得用 Top-1 命中率替代**）：

* 用例可达率 = 至少找得到一个可用候选的用例数 / 有已知适用候选的用例数
* 已知适用候选召回率 = 各用例实际暴露的适用候选数之和 / 各用例已知适用候选数之和

发布门槛（有限验收集）：可达率与召回率 **100%**；选中候选属允许集合 **100%**；
越权实际调用、未知前提误放行、静默换版本 **0 次**；必需审计记录完整率 **100%**；重复执行结果全部保留。

## 8. 验收矩阵

| 编号 | 检查 | 通过判据 |
|---|---|---|
| EX-01 | 已知适用候选可达 | 规定预算内达到可达率与召回率门槛 |
| EX-02 | 排序与选择分离 | 模型按任务与证据选择并有独立决定记录；无程序 Top-1 自动选卡 |
| EX-03 | 未知前提不等于成立 | 记录 `needs_evidence`；可观察，不执行受影响修改动作 |
| EX-04 | 使用版本锁定 | 查询后发布新版不改变已绑定内容；无静默漂移 |
| EX-05 | 越权硬过滤 | 加载或调用被拒并记原因；实际调用数为零（检索加载与实际调用两道） |
| EX-06 | 零结果与错误区分 | 真空集 / 全被过滤 / 后端超时返回不同原因 |
| EX-07 | 截断、分页与预算可见 | 显示截断与游标；不得声称穷尽 |
| EX-08 | 新旧契约隔离 | 只运行所选代际；V2 不调用旧 `judge` |
| EX-09 | 混淆集质量与标签隔离 | 每个负例有明确区分字段；无 oracle 泄漏 |
| EX-10 | 现场变化后的调整 | 模型再观察/再检索并选同方法变体，产生新绑定 |
| EX-11 | 未知效果与资源责任 | 不盲目重建或删除；登记未知效果与资源义务 |
| EX-12 | 输出与记录完整 | 缺证主张不得按完整主张收件；已发生效果仍保留 |

## 9. 对齐成熟自动化框架的工程特征

元数据与实现分离 · 参数与返回结构并实际校验 · 依据已观察状态构造操作 ·
幂等与限制如实声明 · 文档与示例属于发布内容 · 测试分层（静态/检索/决策/集成）· 版本与依赖显式管理。

并且：**可测试 ≠ 可自动回滚，幂等 ≠ 没有副作用。**每张卡必须分别声明：
哪些操作只观察、哪些会创建/修改/删除资源；哪些对象必须清理、哪些必须保留；
什么证据允许清理或恢复；哪些效果不可逆或结果未知；执行体退出后谁继续承担存续义务。
这些不能缩成一个 `cleanup: true`。

## 10. 一张卡“写完并可发布”的判据

方法绑定明确、所有引用可解析、三类输入与构造边界完整、工具范围有实际执行约束、
失败与资源责任有定义、文档与验收用例齐备，并通过 `scripts/check_skill_cards.py`。

## 11. 发布范围（三态，桥 run323 定案）

“卡在册”和“这次发布提供它”是两件事，必须分开说，否则规划层会把一个**声明过不做**的能力
当成“只是还没做”，反复重规划同一堵墙。三态写在 `catalog/release-scope.json`，
由 `src/skills/release.py` 读出、由 `scripts/build_release_map.py` 折进
`catalog/skill-release-map.json`（每张 v2 卡一行）：

| 状态 | 含义 |
|---|---|
| `definition_state=registered` | 卡的定义、契约与变体都在册（不删、不改、历史可读） |
| `release_availability=available\|deferred` | **本次发布**是否端到端提供（`deferred` = 不提供） |
| `runtime_readiness=available\|unavailable` | 运行层现在能不能装载它 |
| `unavailability_reason=FEATURE_OUT_OF_RELEASE_SCOPE` | 延后的原因（当前只用于“会话纳管”这一族） |

纪律：
1. 延后 ≠ 删除：卡的 `status`、契约与变体原样保留，测试仍可引用它；
2. 运行层**拒载**延后的能力并留下原因（`REQUIRED_CAPABILITY_OUT_OF_RELEASE_SCOPE`），
   模型一次都不会被叫到；
3. 交付缺口按“计划真跑过的东西”查三态，命中就把发布范围的话写进缺口行与交接，
   规划层据此**拒选**而不是反复重试；
4. 只声明真不提供的：执行器自己在用的能力不许写进延后清单（有一条反向守线钉住）。

## 泛化守线补充（2026-10-04）

工具调用的绑定单位是实现卡、实现变体、实现工具及实现内容。消费卡的执行点不得决定实现卡的执行点。
目录中的工具契约可用 `provider: {implementation, variant, tool}` 声明提供者；卡的
`execution.tool_bindings[tool]` 声明 `variant_id`、`template_labels`、`tools` 和 `interpreters`。
模板标签精确匹配 SKILL.md fenced block 前的非空行，缺项、歧义或内容漂移须具名拒绝，不得回落到整卡第一条模板。
实现卡的 `runs_at` 与执行声明形成一次执行绑定，工具存在性探测和实际 executor 使用同一绑定；提示中的工具面
同时提供该工具的参数、模板、构造空间及实现摘要。

`accepted_evidence.all_of` 的每个槽位都必须满足；非空 `any_of` 至少一个满足；同时出现两者时二者均须满足。
仅表示替代探针的作者源使用 `alternative_observation_source` 显式生成 any_of，不能依靠引擎扁平化来获得 OR。
事件模式、选择指针、原采集主体、时间及失效 epoch 同属准入条件。前置卡通过不会赋予方法卡新的工具权限：
它只允许方法卡按自己声明的来源消费原证据。图库存里的布尔事实不再直接变成动作车道观察。

无目标绑定的普通卡必须返回 uncertain。`target_verification: {mode: targetless, reason: ...}` 只适用于确实无目标的
操作；不能用该声明豁免已经绑定或已经观察到的目标。服务软件身份、应用身份与各自版本分别判断。


## 第五轮：HTTP 应用身份、版本与运行地址绑定

HTTP 提供者仅采集实际 peer、响应头、正文和编码审计。正文按 Content-Type 声明的 charset 严格解码；无声明时使用明确标记的 UTF-8 默认值。未知编码或解码失败保留原始 bytes，不用替换字符生成可通过的应用身份。采样上限不是完整页面证明。

通用观察卡不内置产品识别表。消费卡可在 contract_v2.application_identities 声明应用身份：id、aliases（可选）、match_any（title/body/path 的 literal 标记），以及可选 version_pattern（含命名组 version）。别名仅将叶期望与声明 ID 对齐，不能代替响应中的标记证据；Server 头只代表服务器软件。采集原文与主体仍须通过原有资格检查；声明缺失、冲突或证据不足保持 unknown。

application_identities 从运行固定的消费卡读取，不能来自模型动作参数。动作车道派生使用原消费契约；legacy 前提检查使用运行侧从候选卡载入的固定声明与叶期望。提供者只收采集参数，不能自行声明某个产品已被证明。

expected_service 用于身份对齐；不会从其 token 中自动推导版本硬要求。需要版本的叶/调用方应显式绑定 expected_version，需要版本的具体方法继续声明独立版本谓词。观察没有产出 application_version 时，身份可单独成立，但显式版本要求及方法的版本准入仍保持 unknown。服务器版本不可代替应用版本。

逻辑主机到部署地址在运行输入交给执行器时绑定。只转换地址语义字段和 URL authority；路径、query、fragment、凭据及结构化 session_ref 不得作为普通字符串递归替换。URL-only 链段导出的 task.host_ref 与证据 required_subject 使用同一个已解析端点。

身份标记的证明范围：path 与解析出的路径精确匹配；title/body 的 literal 是卡作者明确选择的包含型指纹，特异性由卡作者负责，不能把宽泛词语当唯一产品证明。存在冲突身份声明时保持 unknown。固定叶 expected_service / expected_version 优先于模型参数；版本别名不是版本证据。

## 第九轮：来源级观察视角

卡可在 observation_sources 的 subject_bindings.vantage 声明固定位置（例如 base）或 task.source_position；后者必须声明在 input_sources.task，由运行侧绑定图的源位置并在 attempt 内固定。未声明则沿用方法执行绑定的视角，不表示任意位置均可。来源声明只改变该观察的筛选要求，不改变提供者的 runs_at、executor 或回执主体。

例如方法在 base 执行、HTTP 提供者在 position 执行时，应用产品/入口来源可声明 task.source_position；反向部署可用固定 base 观察声明配合提供者 runs_at: base。实际位置与声明冲突会在派生处具名拒绝；运行层不自动把两者互换。model.*、runtime.* 及其他未实现 task 视角引用不被解释为可选择执行位置，返回 UNSUPPORTED_VANTAGE_BINDING。显式绑定缺值及证据缺任何必需轴仍为 unknown。

本轮两张应用方法卡的产品/版本/入口观察显式声明图源视角；可达性、执行身份及完成证据保留方法视角。作者选择的证明范围应与方法需求相符，不能将跳板可见解释为控制点可见。
