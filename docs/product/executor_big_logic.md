# 执行器的大逻辑（定稿 · 2026-09-30）

> 本文是"执行环节怎么跑"的定稿口径，供实现与验收对照。判定依据：本仓代码 + 桥 run273/277/284。

## 一、一句话

**执行环节 = 把"这一步要验证什么"变成"实际发出去的动作"，再把实际收到的东西变成"可信的结论"。**

## 二、大逻辑（七段）

```
①接收执行任务 → ②给现场上下文 → ③提出动作 → ④准备执行 → ⑤执行与采集 → ⑥理解与验证 → ⑦纠正或提交
```

| 段 | 做什么 | 今天谁做 |
|---|---|---|
| ① 接收执行任务 | 拿到"要验证的节点 + 目标 + 允许范围 + 验收条件" | 运行层（图/规划器） |
| ② 给现场上下文 | 把图事实、台账（会话/凭据）、历史尝试整理成执行可用的上下文 | 运行层（选择器 + 供给层） |
| ③ 提出动作 | 选实现（哪张卡/哪种变体）+ 给出参数 | **今天：规则**（按键召回并锁定一张卡，绑定能绑的参数）；**目标：模型可提出同一形状的提案** |
| ④ 准备执行 | 解析引用、补料、绑执行位置、复查权限与状态、装配实际调用 | 运行层 |
| ⑤ 执行与采集 | 派发、采集、超时与取消、保存调用与原始输出 | 运行层 |
| ⑥ 理解与验证 | 解析稳定格式、跑四道闸（新鲜度/目标/身份/效果）、判定通过-不通过-不确定 | 运行层（必要时模型给"解释"，但解释不是证据） |
| ⑦ 纠正或提交 | 失败后换个打法（改参数/换实现/补查/重试/停），成功则登记产出并结算 | 运行层决定"能不能真发生"，模型只能建议 |

## 三、四类记录（分的是类型与写权限，不是四套存储）

| 记录 | 内容 | 谁能写 |
|---|---|---|
| **原始证据** | 实际调用、实际绑定、输出、时间、结束状态、调用关联 | 运行层 |
| **解析观察** | 按规则从证据里解出的字段 + 解析规则版本 | 运行层 |
| **模型解释** | 结论、引用到哪段证据、假设、不确定性、模型版本 | 模型（**不改变证据与判定**） |
| **台账事实** | 被接纳的状态、适用对象与时效、接纳依据、证据引用 | 运行层（唯一提交入口） |

## 四、三条边界（不可越）

1. **标记只辅助关联**：它不单独证明新鲜度/目标/身份/效果；**返回码不能替代效果检查**。
2. **模型摘要不覆盖原始证据**：给模型的上下文若被截断/脱敏，必须标注；截断里没出现的，不等于完整输出里没有。
3. **模型解释要过接纳流程**才算事实；否则只能记成"模型支持的判断"。

## 五、粒度和失败语义

- **一次调用** = 一条命令 + 一份记录（call 目录）。
- **一次节点验证** = 可能几次调用，由反馈决定继续或换。
- **执行生命周期与业务结论分开**：超时/取消 ≠ 不通过；正常结束 ≠ 通过；结果不明先核对，不盲目重放。

## 六、当前实现与目标的差距

| 项 | 今天 | 目标 |
|---|---|---|
| 谁提出动作 | 规则（锁卡 + 绑参数） | 规则**与模型共用同一个提案形状**；模型可改参数/换实现/按反馈改 |
| 命令怎么写 | 24 张写死、11 张模板填空（35 张在册；模板填空的全是核对事实类卡） | 写死的卡**继续保留**；模型不必亲手拼命令，但必须能改变实际行为 |
| 现场适配 | 卡内部各写各的 | 抽一层"现场语义 → 参数/变体" |
| 结果解析 | 各卡各解析 | 稳定格式归代码；无稳定格式由模型给"解释"，原文引用必须保留 |

## 七、最小四步（前三步不依赖在线模型即可验收）

| 步 | 改哪 | 验收（可离线） |
|---|---|---|
| ① | 记录与状态契约分开（执行状态 / 规则判定 / 模型解释 + 调用证据关联） | 标记与返回码正常但缺效果证据 → 仍是不确定；旧输出不满足新调用；重复完成只结算一次 |
| ② | 统一动作提案入口（规则与模型共用；先把规则适配进去） | 提案里的参数/实现一变，**实际派发跟着变**；引用不存在/会话过期 → 不执行 |
| ③ | 观察与反馈视图（现场语义 + 输出片段 + 可回查引用） | 片段能回查原文；缺失与截断明确；换掉模型解释不改证据、不直接登记会话 |
| ④ | 有界反馈循环（先用脚本化决策器，再换真模型） | 拒绝后能修正；预算封顶；取消后不再派发；超时先处理未知效果；迟到输出归旧尝试 |

**已完成的部分**：`run_result.nodes[].proposal` 已经把"本节点打算跑什么"写成上面那个提案形状
（`source / parameter_proposal / implementation / reason`，无卡时是缺口形状）。

## 八、绝不能让模型碰的（一旦交出去，工程保证就没了）

1. 由模型**声明实际执行了什么**，替代运行层的记录；
2. 由模型生成或改写**原始证据、调用归属、时间**；
3. 由模型**绕过**材料解析、会话绑定、权限与状态检查；
4. 由模型自己维护**硬预算、超时、取消、去重、提交一致性**；
5. 由模型仅凭自身解释**宣告通过、登记会话、结算节点**。


> 数字口径：在册 35 张 = fixed 24 + model 11（`skills/index.json` 的 `counts` 可核）。
> 第三方评审（`executor_architecture_review_20260930.md`）指出的两处修正已采纳：
> ①「模型选了卡，但普通节点循环仍从候选列表第一个开始」是真实缺陷；
> ②「模型解释可以被程序采用，但合法引用不等于推理必然正确」。

## 九、落地任务清单（具体到本仓 · 定档 c）

### 9.1 执行器"能做什么 / 不能做什么"（我们的说法）

| 允许 | 在我们这儿具体指什么 | 不允许 |
|---|---|---|
| 挑实现 | 在 `skills/` 里换一张卡（换 `implementation`） | 程序接受后又偷偷换回原来那张 |
| 改参数 | 改**入口明确开放**的参数（等待、重试、端口、路径…），且实现真的用它 | 用 `SKILL.md` 里写了、但机器入口没开的选项；改验收标准 |
| 串联 | 把几张卡按现场串起来（今天是显式链，将来由执行器按现场组） | 自己扩大目标 / 执行位置 / 身份 / 任务边界 |
| 临时脚本 | 本次任务内生成的小脚本（解析、计算、组合） | 自己新增对外入口；绕过运行层直接对外动手 |
| 按反馈改 | 看失败原因改参数 / 换实现 / 改顺序 / 停 | 改历史证据；自己宣布"成功" |
| 恢复 | 按卡声明的语义核对 / 安全重放 / 停 | 把"已派发但结果未知"当失败直接重跑 |

一句话：**很长但没新增对外入口 = 还是 c；很短但新增了对外入口 = 越过 c。**

### 9.2 三件事分开：落到我们已经有的文件上

| 三件事 | 本仓的落点 | 谁读 |
|---|---|---|
| 能力知识（有哪些方法、怎么选、失败经验） | `skills/<id>/SKILL.md` | **模型** |
| 工具实现（真跑的东西） | `skills/<id>/entry.py`、`client/`、`poc/` | **运行层** |
| 验收要求（怎样算完成） | `skills/<id>/skill.json` 的 `judge` + `src/graph/objectives.py` 的目标契约 | **验证侧** |
| 机器可调项（唯一真源） | `skills/<id>/skill.json` 的输入声明 | 运行层（并据此**生成**给模型看的说明） |

**防漂移**：参数只在 `skill.json` 定义一次；`SKILL.md` 里写的"可调"必须指向它；
被实现忽略的参数一律不算开放（**验收动作：改一次参数，看实际调用是否跟着变**）。

### 9.3 修改面（新增一个实现，应当只改三处）

```
skills/<new-id>/…（新目录）  +  skills/registry.json 加一行  +  重新生成 skills/index.json
```
**不许动**：`scripts/run_path.py`（执行器）、`src/runtime/checker.py`（判定）、`src/agents/*`（角色契约）。
**验收动作**：接入一个新实现，`git diff` 应当只落在上面三处。

### 9.4 三份记录（提案 / 回执 / 判定）在我们这儿的现状与缺口

| 记录 | 今天在哪 | 缺口 |
|---|---|---|
| 提案 | `run_result.nodes[].proposal`（本轮已加） | 提案 → 实际调用**没有显式对应** |
| 回执 | `node-N/attempt-*/call-*/call.json` + 台账登记 | 没有 `proposal_ref` / `attempt_id` 链 |
| 判定 | `judgement.json` / `verdict.json` + 目标收尾闸 | 缺"模型改了什么"的差异记录（应由程序比对生成） |

### 9.5 最短闭环（拿一个真实节点当样板）

1. 选**一个有真实失败案例的节点**（建议"关防御设置"那个：它既有成功，也出现过"工具跑了但效果没到"的不确定）；
2. 让它先失败一次，把失败原因喂回去；
3. 模型/脚本化决策器**改参数或换实现**；
4. 运行层照提案执行；
5. 独立判定（四闸 + 目标契约）通过 → 闭环成立。
**先用脚本化决策器跑通，再换真模型。**

### 9.6 不依赖模型就能先验收的六件事（我们的具体测法）

1. 注入"换实现" → 看实际发出的命令是否换成新实现；
2. 注入一条失败观察 → 下一轮提案里能看到它；
3. 自报成功但四闸不过 → 节点**不能**结算（这条今天已成立，实测过）；
4. 预算耗尽 / 超时 / 取消 → 不再派发，已有动作状态明确；
5. 派发与回执之间中断 → 恢复后能区分"没发 / 发了 / 结果未知"（今天只有进程内的 unknown 记录）；
6. 回放记录 → 能还原每次决定的依据与实际发出的命令。

### 9.7 切片顺序（改哪、验什么）

| 切片 | 改哪里 | 验收 |
|---|---|---|
| ① 基线 | 给现有调用补**参数、版本、回执、证据引用**；行为不变 | 原有结果不变，每个结论可追到原始调用 |
| ② 能力组织 | `skill.json` 增加方法分组与**开放参数**；生成给模型看的调用视图 | `SKILL.md` 里写的可调项**真的能调**；底层实现粒度不变 |
| ③ 单节点闭环 | 用脚本化决策器走"失败 → 改法 → 执行 → 独立判定" | 提案变了，**实际派发跟着变**；预算/取消/中断可分辨 |
| ④ 接真模型 | 把决策来源换成模型，契约不变 | 在保留案例里完成一次真实的"失败→改法→通过" |
| ⑤ 补齐 c | 串行组合 + 临时脚本两条通路 | 两条路都有完整记录与独立验收 |
| ⑥ 合并能力 | 按重复代码与真实调用轨迹合并 | 老契约样例不变，接入修改面变小 |
| ⑦ 三角色 | 等预算对照实验 | 达到预设门槛才保留 |

**⑤ 没完成前，不宣称"交付 c"。**


## 本轮执行绑定边界（2026-10-04）

动作车道先冻结具体工具实现和供给面，再由实现卡的执行声明绑定 executor。消费卡只给出任务与工具需求。
工具探测、命令装配和实际执行必须共用该绑定，记录实现摘要；绑定变化需新运行，不可在原尝试内静默替换。
pre.service_version 的横幅、HTTP 响应及键值协议响应是三个具名提供者路由，各自只暴露对应模板和所需工具。
HTTP 应用观察绑定 response_probe / probe_service_response，不得落回 nmap 横幅模板。

这一边界不承诺任意环境只改卡：新的执行通道、解释器适配与事实判据仍需实现和独立测试。
现有后端没有原调用查询能力时，恢复路径保留 unknown 并报告具名缺口；查询回执结清副作用也不自动证明节点目标。
