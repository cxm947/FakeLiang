# 用 S1 把任务怎么运行讲明白

> 这是 v0.3 简洁方案的说明，运行层尚未实现。下面讲的是准备开发的行为，不是已经跑通的实验结果。

先抓住一句话：**程序拿着攻击图安排任务，大模型负责把当前任务做完，数据库记住做到了哪里、凭什么说做到了。**
模型不用记住整条攻击路线；换一次模型上下文，也能从图和数据库重新取得该知道的内容。

## 1. 已经处理好的 TXT，接下来直接用

现在的 TXT 已经被转换成 V1 `action_graph.json`。这份 JSON 就是运行的输入，不再重新设计一份攻击图。
其中 `source_graph` 留着原始事实和规则，`nodes` 留着投影后的节点；节点的 `semantics` 写着前提、效果和依赖。
`requires` 告诉程序要等哪些前驱；`premise_refs` 用来找当前节点直接涉及的条件；`effect_refs` 告诉程序成功后应该证明什么。
因此，目标主机、来源主机、规则类型和原始事实描述，都从现有 JSON 读，不再在数据库各复制一遍。

这里说“节点 21”，是为了方便人看原图编号。程序实际引用的仍是 V1 已有的节点 ID，不另外发一套任务编号。
原图里 LEAF 的 `metric=1`，以及投影阶段“LEAF 固定成立”的假设，不代表我们已经在靶场核实过它。
运行时仍要检查当前节点需要的 LEAF；只是本次运行接受了这些前提后，不再维护一套随时间自动失效的事实系统。

## 2. 数据库只记三本账

| 账本 | 用大白话说存什么 |
| --- | --- |
| `runs` | 这次用哪张图、哪些配置，现在是否暂停、正做哪个节点的哪一段，以及已核对的 MSF 会话 |
| `node_runs` | 图中每个 AND 节点现在做到哪了、没做成的原因、最终结论对应哪条记录 |
| `records` | 模型说了什么、工具收到了什么和返回了什么、程序怎样检查、最后怎样结案 |

`runs.graph_json` 原样保存这次输入，`config_json` 保存这次使用的配置；运行中不改图来迁就结果。
节点结果只保存状态、原因和记录引用。终点 OR 是结果展示，程序算出来即可，不再复制成待执行任务。
`records` 用数据库自增编号排序，类型只有 `agent/tool/check/result`；具体输入、输出和结论放在 `data` 中。
短内容直接存数据库，大日志和文件放本地目录，记录里保留文件引用；不用把完整材料塞进模型对话。

“现在进行到哪里”只记一次：`runs.current` 中的节点 ID、阶段，以及当前记录编号。
阶段只有 `pre/action/post/session`，分别表示前检查、动作、后检查和会话准备。没有正在处理的工作时，`current` 为空。
这三本账各司其职：看 `node_runs` 知道进度，查 `records` 知道根据，读 `runs.current` 知道怎样接着做。

## 3. 谁选任务，谁完成任务

**主控程序选下一个节点。** 它读原图依赖和已提交的节点结果，在可推进的节点中按原始编号排序。
它不会问模型“你觉得下一步攻击哪里”。同样的图和已接受结果，会得到同样的依赖判断和候选顺序。
这里的“可以开始”是即时计算的，不在数据库再存一个 `ready` 状态。

**Execution Agent 完成当前节点。** 程序把该节点的目标、前提、要证明的效果和可用上下文交给它。
它调用工具检索功能，选择兼容方法，完成前检查、动作和后检查；一次节点任务中可以有多次工具调用。
工具列表里没有合适方法，就说明缺什么；不能换一个容易的目标，也不能省掉图中要求的效果。

**Checker 是程序判据。** 模型提供观察与解释，程序按约定检查证据是否足以支持结论，再负责写入结果。
正常节点证据齐全，就直接提交成功，不必再找一个 Reviewer 模型重新评价一遍。
**Supervisor 只在需要时分析异常。** 它可以建议补检查或调整方法，主控核对建议后再让当前 Agent 继续。
Supervisor 不能改依赖、换验收条件或凭一句判断让后续节点解锁。

## 4. S1 为什么会按这个顺序走

在各节点都能成功、会话准备也完成的情况下，S1 的 AND 顺序是：

`2 → 14 → 12 → 7 → 24 → 21 → 31`

| 节点 | 本节点要证明的内容 | 成功后怎样帮助后续任务 |
| --- | --- | --- |
| 2 | 图中定义的攻击入口条件，即 fact 1 | 节点 14 的前驱条件满足 |
| 14 | `.10` 上图中要求的 admin 执行能力，即 fact 13 | 节点 12 可以继续验证 |
| 12 | `.10` 上的 system 执行能力，即 fact 11 | 节点 7、24 的相关依赖满足 |
| 7 | `.11` 的防火墙处理结果，即 fact 6 | 满足节点 21 所需的一组前驱条件 |
| 24 | 图中规定的凭据获取结果，即 fact 23 | 节点 21、31 可以继续判断 |
| 21 | `.11` 上的 system 执行能力，即 fact 20 | 对应终点结果成立 |
| 31 | `.12` 上的 system 执行能力，即 fact 30 | 另一个终点结果成立 |

节点 7 和 24 都有机会继续时，先选编号较小的 7。节点 7 完成后，21 仍在等 24，所以接着做 24。
24 完成后，21 和 31 都进入候选，再按编号先做 21。不是“21 永远排在 24 后”，而是依赖先限制范围，编号再决定顺序。
会产生新执行入口的节点，成功后还要立即处理会话，再回到上述调度流程。

## 5. 把节点 21 从头走一遍

程序先读节点 21 的 `requires`：这里要同时满足节点 7 提供的 fact 6、节点 24 提供的 fact 23。
程序看到这两个节点已经提交成功，就能从图推导相应 OR 事实成立；不用再去另一张事实表更新两个 true。
节点 21 的原始前提还包含 fact 11。V1 已记录它被 fact 6 的依赖链覆盖，这个关系来自图的化简，不能由模型临时猜测。

接着，程序将节点 21 记为 `running`，把 `current` 指向它的 `pre` 阶段。
Execution Agent 读这个节点自己的直接 LEAF：22、28、29，分别核对账户条件、来源到目标的连通条件和目标服务条件。
它不重新把所有祖先的 LEAF 查一遍。已经接受的检查可以复用，尚未检查的条件再取证。
程序接受的检查记录用 `true/false/null` 表示成立、不成立、无法判断；模型未经检查的推测不能充当这个值。

这些条件成立，并且方法和执行资源都合适，才能进入 `action`。缺工具或缺会话就说明缺什么，不假装图中的效果已经完成。
这一步来源是 `.10`、目标是 `.11`。程序按来源、身份和能力找上下文，不能随手拿一个活跃会话代替。
图中写的是 `winrm/139`，保持原样；确有靶场端点映射时由配置明确提供，不能静默改成别的端口。

动作返回后进入 `post`：取证并核对 effect 20，确认 `.11` 上取得的是图中要求的能力。
只看到工具输出“成功”还不够；后检查要提供判据需要的证据。如果有多个必需效果，必须全部通过。
程序随后在同一个数据库事务中保存结案记录、把节点 21 改为 `succeeded`，并让 `result_record_id` 指向该记录。
从这一刻起，程序可由节点 21 的成功推导 fact 20 成立；终点 20 的展示也随之成立。

## 6. MSF 会话在什么时候接手

如果节点 21 得到了新执行入口，刚才的成功事务同时把 `current` 改到节点 21 的 `session` 阶段。
这样，即使程序马上中断，下次也知道“验证已成功，会话还没处理”，不会把节点 21 再执行一遍。
Session Agent 通过已有入口建立 MSF 会话；如果已有符合条件的 MSF 会话，就复用并核对。
核对主机、身份和能力后，才把它登记到 `runs.sessions`。数据库记的是映射，实际连接仍由 MSF 持有。

会话准备成功或明确失败，都写一条记录；处理结束后清空 `current`，主控再选下一节点。
会话失败不抹掉节点 21 已经证明的结果，失败原因放在 `records`，也不往会话目录放一个冒充可用的条目。
后续任务需要的会话没有准备好，就按资源不足处理；具备条件的其他分支仍可继续。
S1 的节点 31 来源仍是 `.10`，所以即使刚建立了 `.11` 的会话，也不能默认拿最新会话执行节点 31。

## 7. 出问题和中断分别怎么办

节点只保留六种状态：`pending/running/succeeded/failed/blocked/uncertain`。
前两个表示尚未处理或正在处理；成功要有证据；反证支持失败；条件或能力不够写 blocked 并说明原因。
`uncertain` 表示已经确认没有在途调用，但现有证据不足，而且本轮不再继续这个节点。
工具超时不自动等于失败，也不能马上结成 uncertain：工具可能仍在工作，只是结果还没返回。

因此，每次工具调用前先保存调用记录，再发出调用；收到结果后保存返回内容并继续检查。
如果前检查、动作或后检查中断，无法确认外部调用是否已经执行，就让 run 处于 `paused`，节点保持 `running`，保留 `current`。
如果未知的是后面的会话准备调用，run 同样暂停并保留 `current`，但原节点仍是 `succeeded`，不能退回正在验证。
恢复后先查询原调用或进行必要的后验核对；无法判断就继续暂停，不能换个调用重新发一遍动作。
如果结果已经保存，只是节点还没结案，就继续后检查和提交；如果已经进入 session，就只恢复会话工作。

本版假定一次 run 的前提和效果在验证过程中保持有效，不做定时失效或自动撤销链。
发现与已接受结论冲突的环境变化，就暂停核对，必要时重开 run；MSF 掉线本身不等于图中事实被反证。
能做的节点都处理完、剩下节点的阻塞原因也已明确，而且没有在途工作时，run 才记为 `finished`。
`finished` 只表示本轮结束；报告仍分别列出成功、失败、阻塞、不确定和会话问题，不把它们合成一个模糊结论。

## 8. 读懂之后，应该能说清这几件事

程序检查图依赖后选中节点 21；后检查证据通过并已提交，才能说节点 21 成功。
事实的原始含义在图里，LEAF 检查在记录里，OR 结论从成功节点算出来；当前工作位置看唯一的 `current`。
换模型后，程序重新给它当前任务；路线和完成记录一直在数据库中，不靠模型记忆接力。
MSF 准备失败保留原节点的验证结果；它影响后续执行资源，原因单独记录。
